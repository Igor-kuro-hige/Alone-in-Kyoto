КАК СО МНОЙ РАБОТАТЬ (прочитать в первую очередь)
Игорь пишет код сам. Направляющие вопросы вместо готовых решений, особенно по уже пройденным темам. Код показываю только когда сам застрял после пары попыток
Формат каждой темы (согласован в октябре 2026): объяснение → 2–3 задачи после него, задачи нарастают по сложности вплоть до уровня реальных проектных. Тема считается закрытой только когда задачи решены без подсказок и он объяснил решение своими словами
Глубина важнее скорости. Игорь сам заметил, что мы закрывали темы на паре простых примеров (spread/rest, destructuring и более ранние). Договорились: у каждой темы три уровня — 1) основа, 2) типичное использование в реальном коде (особенно React), 3) ловушки. Не ставить "пройдено" после уровня 1. Ранее пройденные поверхностно темы возвращать через задачи, а не через повторную теорию
Порядок: теория → практика на его реальном проекте. Если тема не находит места в проекте — вместе придумываем, куда встроить
Часто путает похожие имена при сборке кода из кусков (allArticles/articles, category/categories, задвоенные response/html) и пропускает запятые/скобки при спешке — типичная точка для подсказки "ищи вот здесь", не критика
Голова хуже работает вечером/на усталости — вечером лёгкие задачи и повторение, не новая тяжёлая тема

КРИТИЧНО: весь код, зависящий от элементов из header/footer (musicBtn, form, articles, radio-логика), идёт ПОСЛЕ обоих await fetch+await .text()+innerHTML, в конце файла initPage();. reduce: самая тяжёлая тема из методов массивов. Закрепилась на примере группировки слов (cat/dog/cow/ant/cup) по первой букве; если путаница вернётся — опираться на этот пример. Пришлось отдельно разбирать array (доступ по номеру) vs object (доступ по имени-ключу). К allArticles (группировка по category) ещё не применяли

spread/rest: уровень 1 (spread для копирования массива/объекта и перезаписи поля, rest в деструктуризации let [first, ...others]). Уровни 2–3 в работе (см. ниже)

ПЛАН ПО JS (до React)

Группа A, обязательно до React:

spread/rest уровни 2–3: rest-параметры функций (function sum(...numbers)), spread в вызове (Math.max(...nums)), слияние объектов и порядок перезаписи, поверхностная копия (вложенные объекты/массивы остаются общими с оригиналом), rest всегда последний. Идея для проекта: поле tags в статьях + функция addTag(article, tag), возвращающая НОВУЮ статью без изменения оригинала (тот же паттерн, что обновление состояния в React)
modules (import/export) — без них React-проект не запустить
замыкания и scope (на них держатся хуки), this в минимальном объёме (почему в стрелочной функции иначе)
Promise глубже: .then/.catch, Promise.all, проверка response.ok, try/catch при fetch
ПОВТОР через задачи: destructuring (ловушки), reduce на allArticles, map/filter/forEach на задачах посложнее

Группа B, параллельно по ходу проекта: JSON и fetch с настоящего API, find/some/every/includes, ?. и ??, truthy/falsy, localStorage, всплытие событий и делегирование. Группа C, позже: классы, регулярные выражения, дженерики.
